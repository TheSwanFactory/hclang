# Review: `apply-new.hc` as Design Fiction

**Status:** Review. Reads `cli/hc/apply-new.hc` as a design document and a
teaching document, not as a test result. Nothing here was executed; every
"currently" below is what [`apply.hc`](../cli/hc/apply.hc) records as v0.14.1,
which is itself a document.\
**Issues:** [#368](https://github.com/TheSwanFactory/hclang/issues/368), with
[#374](https://github.com/TheSwanFactory/hclang/issues/374) adjacent.\
**Reviews against:** [`a11.3`](a11.3-key-properties.md) as the chosen semantics,
[`a11.1`](a11.1-receivers.md) as the operator spelling under consideration,
[`a11.2`](a11.2-declaration-receipt.md) as the diagnosis, [`a11`](a11-resource-iteration.md)
as the character-fold parent, and [`a10`](a10-resource-primitive.md) for what a
resource publishes.\
**Verdict:** The model is coherent and the file is the right artifact. Three
design questions are unanswered inside it, one expectation appears to contradict
a10, and the closing third of the document asserts rules it never demonstrates.

## What the document already does well

The two-axis framing is the document's real contribution. `a11.2` left the
operator question unanswerable because the value had two planes with no stated
division of labor; `a11.3` fixed the value; this file is the first place the
operator surface reads as **two independent questions** rather than four glyphs
to memorize. The table earns its position at the top.

Three specific strengths worth preserving through any revision:

- **"Application is still the one verb" comes before the operators.** A
  value-seeded fold is otherwise unmotivated magic. Establishing `“” “h”` and
  `[] 1` first makes `| “”` and `| []` derivations rather than features.
- **The `$!.unimplemented` convention is explained where a reader meets it**,
  and the mechanism it describes — report without failing, fail when the
  behavior arrives before the marker is removed — is exactly the right contract
  for design fiction. It makes the file a ratchet instead of a wish.
- **The scoping refusals are honest.** "This proposal does not settle whether
  *every* plain statement should be non-enumerable," followed immediately by
  `[1; 2;]` → `[(1); (2);]` as a preserved invariant, is the best paragraph in
  the document. It names an open question, then shows what it is deliberately
  not touching. The other open questions below deserve the same treatment.

The unmarked expectations are also doing more work than the document claims. A
reader can find what the redesign promises **not** to break by looking for lines
without a marker. That is a genuine feature of the format and it goes unsold.

## Design questions the document leaves open

### 1. A resource's `&&` appears to contradict a10

This is the sharpest problem. The doubled form is defined as *every public
addressable entry: visible named properties first, then indexed positional
elements*. Per a10, `FrameResource` extends `FrameURI` and publishes RFC 3986
`scheme`, `authority`, `path`, `query`, and `fragment` as properties.

So the rule predicts that `'./out.txt' && {_}` begins with the resource's own
property entries. The document's expectation is characters only:

```
; './out.txt' && {_}
# $!.unimplemented [[0, “h”], [1, “e”], [2, “l”], [3, “l”], [4, “o”]]
```

One of these is wrong, and either answer is interesting:

- If URI decomposition properties **are** public entries, the expectation needs
  the property prefix, and the doubled form over a resource becomes a strange
  hybrid of identity and content.
- If they are **not**, then "public" is load-bearing in a way the document does
  not admit. a11.3 §6 excludes schema companions, structural links, and
  interpreter bookkeeping — none of which describes `.path`, which is a
  documented user-facing read. A third category is being introduced silently.

There is a deeper version of the question underneath: **what are the properties
of a stream?** For an aggregate, the complete view is a finite value's two
address spaces. For a resource, the positional half is a fold that may not
terminate and the named half is metadata about the reference rather than the
content. Calling both "the complete addressable entry view" may be an
overreach that only shows up here.

### 2. Does `&` still expose an index?

In the spelling `apply.hc` records, `|` maps with the element in `_` and the
zero-based index in `.`, so `[1, 2, 3] | {. }` is the indexed map. Under the new
assignment `&` maps — and every `&` example in the file uses only `_`.

If `&` drops the index, indexed mapping moves to `&&` and `{_.1}`. That is
coherent, and it is probably the intent, because it is what makes `&&` worth
having for maps at all. But it is an ergonomic regression on a common case and
the document should own it rather than leave it inferable from absence.

If `&` keeps the index in `.`, then `&&` is redundant for maps over
property-free lists, which weakens the two-axis story considerably.

Either way, one sentence. As written, a reader cannot tell which.

### 3. The refusal the prose demands has no spelling

> An aggregate seed belongs to fold, not map. A map wraps one answer per input;
> using a stateful aggregate there would repeat aliases to the same accumulator
> and should be refused rather than half-work.

Correct, and unenforced. Under the new glyphs the mistake is spelled
`[1, 2, 3] & []` — which is **the current fold spelling**, so it is the single
most likely thing a reader of `apply.hc` will type. It deserves an expectation
and a named refusal value, something in the shape of:

```
; [1, 2, 3] & []
# $!.unimplemented $!.aggregate-in-map
```

Prose that says "should be refused" in a file whose premise is executable
claims is the weakest form the claim can take.

### 4. Aliasing of a value seed is unspecified

`apply.hc` makes one distinction central: **text answers a new value; an
aggregate answers itself.** This file reproduces the examples (`“” “h”`, `[] 1`,
`[1] 2`) but drops the distinction, and it matters more here than there, because
`| []` threads the accumulator as the receiver.

Every seed in the document is a fresh literal, which sidesteps the question
a11.1 flags as open under "Reuse": if a seed is *named*, does the fold mutate
it? `[] | []` versus a bound accumulator are different programs, and the
document's silence reads as an answer when it is not one.

Related and also absent: `apply.hc` records that a void argument is not
collected (`[] ()` → `[]`). In a fold that becomes a real rule — what happens
when a block answers nil mid-fold, or when a nil element reaches an aggregate
accumulator? Skip, or become the accumulator?

### 5. `||` has no block form

`&&` gets both a tuple-identity example and a projection example
(`{_.1 * 2}`). `||` gets only value seeds. The missing case hides a real
question: **what seeds a block-form `||`?**

The single fold seeds from the first element, so by symmetry `||` seeds from the
first entry — making the initial accumulator a `[key, value]` tuple, which is
almost certainly not what anyone wants. Either `||` requires a value seed (say
so, and say what a block form refuses with), or first-entry seeding is
deliberate and needs the example that makes it look sane.

### 6. The complete view has no inverse, and the document implies one

The tuple claim is stated carefully — "synthesized for iteration; it is not the
stored representation" — and it is true of the source. It is *false* of the
result: `&&` answers real nested arrays. That gap is fine, but the document then
says the doubled form makes "identity complete-entry iteration an actual
identity over entries," which invites the obvious next move: fold the entries
back to rebuild the value.

`a11.2` already establishes that this does not work — applying a pair does not
merge, and `(.z 9) (.a 1)` loses `.z`. So there is no inverse, and the file that
teaches the complete view is the right place to say there isn't one. Otherwise
the first reader to try round-tripping discovers a wall the design knows about.

### 7. Two rules that would be stronger as one

The numeric-key refusal reads as an unmotivated edge ruling:

> an integer key on a list refuses rather than hiding behind an index

But the doubled form puts names and indices **in the same slot**, so a `||` fold
that dispatches on the key type is only safe because the two key spaces are
disjoint. The refusal is what buys that. Stating it that way turns an edge case
into the reason the complete view is well-formed at all, and it belongs in the
`&&` section rather than in a closing bullet.

### 8. Does a string enumerate its characters?

`a11` lists this as an open decision and says the asymmetry "needs either a
reason or a fix." This document establishes that a resource read is a character
fold and stays silent on `“abc” & {_}`, which `apply.hc` records as `[“abc”]`.

A tutorial that introduces character folds should state its position, even if
the position is "unchanged, and here is the invariant." As written, the resource
section reads as though characters are the universal element, and a reader will
generalize accordingly.

## Coverage against a11.3's acceptance boundary

The file is the natural home for a11.3's eight acceptance criteria. Four are
covered, four are not.

| a11.3 acceptance                                | In the file    | Note                                                     |
| ----------------------------------------------- | -------------- | -------------------------------------------------------- |
| 1. `[.meta 1; 2, 3]` iterates `2, 3`, `.meta` works | yes        | the anchor example, used consistently                    |
| 2. same value's complete view                   | yes            | both `&&` and `\|\|`                                     |
| 3. rebind never touches an element              | yes            | `[.a 1; a, .a 2]`                                        |
| 4. named and positional with one read           | yes            | `[.a 1; a, 2]`                                           |
| 5. `^`, schema, constants, visibility, handles  | **partial**    | constants and schema only, and only inside a closure     |
| 6. `==` needs no declaration-string heuristic   | **absent**     | a11.3 §8 defines `==`/`===`/`=` across the two planes    |
| 7. key/index plus value, no stored pairs        | partial        | tuples shown; "not stored" asserted, never demonstrated  |
| 8. no third persistent plane                    | n/a            | not observable from source                               |

Three specific omissions are worth more than the others.

**`^` is missing, and it is the reason the receipt existed.** Per a11.2,
`FrameLiteral.binding` has exactly one consumer — `^` — and the vestigial write
log in every aggregate exists to give that operator an lvalue. This document's
central move is that successful declaration evidence is *consumed* rather than
stored. A reader who understands why the receipt was there will immediately ask
whether `.f (sig) ^ {body}` survives. a11.3 §1 and acceptance 5 say it must.
One expectation would close it.

**Failure preservation is shown in the wrong container.** a11.3 §5 rules on the
*constructor*: `[.A 1; .A 2;]` must not become an apparently successful object
holding `A` → `1`. The file demonstrates `{.A 1; .A 2; 3}()` instead, which is a
closure and a different code path. The normative case is untested.

**The case that decided the design is absent.** `[.a 1, 9, .a 2]` is the row in
a11.3's table and the "case that decides it" in a11.2. The entire rejection of a
permanent key-to-slot map rests on it. Teaching the conclusion without the case
that forces it leaves the minimax argument invisible — the reader sees a rule
where there was a trade.

Cheaper additions in the same spirit: `[[.a 1;], 2]` for nested ownership
(prose-only today), a numeric-key refusal, `[] && {_}` and `[] || []` for the
empty complete view, and `[.a 1] & {_}` — the property-only aggregate, where the
two views diverge maximally and which is the shortest demonstration that
properties are not elements.

## The pedagogy

### The glyph swap is never announced

This is the highest-value fix in the review, and it is one sentence.

`apply.hc` — named in this file's second sentence, sitting in the same directory
— records `|` as map and `&` as reduce. This file uses `&` for map and `|` for
fold. The bullet list states the new assignment; nothing anywhere says **it is a
reversal**. a11.3 does say so ("deliberately differ from v0.14.1; the current
behavior remains documented in `cli/hc/apply.hc`"); the tutorial dropped it.

A reader who knows 0.14.1 will silently misread every operator example in the
file, and the misreading is self-consistent, so nothing will correct them. The
header needs an explicit warning, not an implication.

The same swap makes two neighbouring documents actively misleading, and a
pointer costs little: `a11` still argues in the old spelling throughout
("`|` maps, so mapping a character source already answers an array of
characters", "`& “”` → the whole content"), and `resources.hc` still spells
reads with the old roles. a11's scope list already carries "`resources.hc`
re-spelled" as a checkbox; this file's resource section is effectively that
target spelling, and saying so links them.

### The cold open asks too much

Four expectations land before "property" or "element" has been defined, and the
fourth is `|| []` — a value-seeded fold over synthesized tuples, which is the
least obvious spelling in the whole design. The reader's first concrete
encounter with the model is its hardest corner, ~200 lines before the machinery
that explains it.

The table should stay; it is the map of the document. The examples would work
better either deferred to a summary after "Properties are not elements," or
marked plainly as a forward reference the reader is not expected to parse yet.

### Section order splits the table's own rows

Sections run `&`, `&&`, `|`, `||` — column-major, so the doubled map arrives
before the single fold, and the `&&` section has to forward-reference folding to
explain why the tuple exists.

Row-major (`&`, `|`, then `&&`, `||`) matches the "two independent questions"
framing the document opens with, lets the two doubled sections share one
explanation of the synthesized tuple, and puts the accumulator convention in one
place instead of two.

### Terminology proliferates

Four names for two concepts:

- *enumerable elements*, *scalar elements*, *positional elements*, *scalar
  element*
- *complete entries*, *complete addressable view*, *public addressable entry*,
  *complete-entry form*

Pick one name per concept, define it once, and use only that. "Positional
element" and "complete entry" are the two that carry the most meaning per word.

One more drift: *declaration receipt* appears once, in the parentheses section
("when its declaration receipt leaves the data plane"), while the rest of the
document says *declaration evidence*. a11.3 retired "receipt" — a11.2's term for
the defect — in favor of "evidence" for the transient internal value. The
leftover reads as a third thing.

### "Answers its last successful result" is contradicted two examples later

> A closure executes each statement and answers its last successful result

Then, six lines down, `{.A 1; .A 2; 3}()` answers `$error{$is-constant .A}` —
even though `3` is the last statement and it succeeds. The rule is *answers its
last result; a failure aborts execution and propagates*. The word "successful"
was inserted to gesture at the failure case and gets it backwards. Since the
same section is where the document explains that failed declarations are never
consumed, the imprecision lands at the worst possible spot.

### The closing list is the weakest passage

"Edge rules, all from one separation" is eight assertions with zero
expectations, in a file whose entire premise is that claims are executable. Four
of the eight are cheap to demonstrate — nested ownership, two names for one
value, failure preservation, the numeric-key refusal. The remaining four
(structural parent, canonical rendering, parsed frame graph, manifest analysis)
are genuinely prose, and belong in a11.3 with the other normative rules rather
than in the tutorial's last screen.

As it stands the file's final impression is a list of things the reader is asked
to take on faith, immediately after 200 lines of things they were not.

### Missing orientation

There is no line telling the reader how to read the file: that every marked
expectation is a promise rather than a bug, that the file is wired into
`test:doc`, and that a large marked count is the point. `apply.hc` has the same
gap and needs it less, being a record of what is.

## Minor

- The header table uses a bare `|` inside a cell (`| `&` | `|` |`). a11.1 and
  a11.3 both escape this as `&#124;`. If the header is ever rendered as
  Markdown, the table breaks.
- `&&`'s motivating defect is missing. a11.2's headline symptom is
  `(.a 1, .b 2) && {_}` answering `[1, 2]`. The `&&` section never shows the
  repaired version of that exact expression, so it reads as a new feature rather
  than a fix. Adding it connects the tutorial to its own diagnosis in one line.
- `[.meta 1; 2, 3] & {_}` appears twice, once in the cold open and once under
  "Properties are not elements." Harmless, and arguably deliberate, but if the
  cold open is restructured the duplicate should go.
- #374 is mentioned once, mid-example. The parentheses section makes ownership
  claims that #374 could disturb; a one-line boundary note would protect it the
  way the statement-suppression paragraph protects itself.
- "Public is important" carries the whole visibility story in one aside. Given
  that item 1 above turns on exactly what "public" means, it deserves a
  demonstration — a private or protected key that `&&` declines to enumerate.

## Suggested sequence

Ordered by value per edit, not by section position.

1. Announce the glyph swap in the header, with a pointer to `apply.hc` for the
   current spelling and a note that `a11` and `resources.hc` still read the old
   way.
2. Resolve or explicitly defer the resource `&&` question (item 1). It is the
   only place the design looks internally inconsistent rather than incomplete.
3. Fix "last successful result."
4. Answer the index question for `&`, the seed question for `||`, and the
   aliasing question for value seeds — three sentences, or three explicit
   deferrals in the style of the statement-suppression paragraph.
5. Add the four missing expectations that carry the most argument: `^`,
   `[.a 1, 9, .a 2]`, `[.A 1; .A 2;]` in an aggregate, and the refused
   aggregate-in-map.
6. Collapse the terminology to two names per concept.
7. Reorder to row-major and convert half the closing bullets into expectations.

None of these change the model. The design in this file holds up; what it is
missing is the small number of places where it knows more than it says.
