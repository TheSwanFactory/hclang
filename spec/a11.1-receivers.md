# Receivers: A Brainstorm

**Status:** Brainstorm. Nothing here is decided, and options are recorded
alongside their costs rather than filtered down. To be merged into
[`a11`](a11-resource-iteration.md) once the shape settles, at which point this
document goes away.\
**Issue:** [#368](https://github.com/TheSwanFactory/hclang/issues/368)\
**Relation to a11:** a11 enumerates _what_ receivers do. This asks what a
receiver **is**, how one gets named, and where it comes from.\
**Blocked by:** [`a11.2`](a11.2-declaration-receipt.md). A keyed-versus-unkeyed
operator split is the most promising idea here, and it cannot be designed
against a value whose two planes are a dictionary and a log of the writes that
built it.

Three tracks, which are not exclusive and probably all land in some proportion:

1. The runtime `Frame` object, which kind of exists already.
2. Special syntax — operators or globals — for the common cases.
3. Integration with the existing eval objects.

## First: "receiver" already names three protocols, not one

This is the thing to settle before any of the three tracks means anything. The
codebase has three receiver-shaped protocols and they do not agree.

| Protocol        | Accepts                     | Answers          | Completion    | State           |
| --------------- | --------------------------- | ---------------- | ------------- | --------------- |
| **Lexical**     | one symbol, plus the lexeme | a `ScanResponse` | `finishInput` | in the frame    |
| **Application** | a value and a parameter     | a frame          | none          | none by default |
| **Pipe**        | a value, or a marker key    | emits to `out`   | `finish`      | pending fields  |

**Lexical** is `scan` / `finishInput`, routed by the `Sigilizer`. Its default is
on `Frame` and returns the frame unchanged, so every frame is nominally a
lexical receiver. Real ones: `Lex`, `LexRun`, the counted `FrameBytes` receiver,
and `Malformed`.

**Application** is `call` / `apply`. Also universal, and it is what a block is:
`&` hands a block the element with the accumulator in the parameter slot. It has
no completion step at all, which turns out to matter.

**Pipe** is a convention rather than a protocol — a constructor taking `out`,
emission through `out.call`, and a `finish` that flushes. `LexPipe`,
`ParsePipe`, `EvalPipe`, and `HCTest` all follow it. `HCTest` additionally
receives by `set` on marker keys, which is a fourth shape if you are counting
strictly.

Whichever one the fold uses, the other two still exist and will have to be
adapted or deliberately ignored. There is no option that avoids choosing.

## Track 1: the runtime `Frame` object

**What exists.** The lexical protocol, with a universal default, a router, a
failure receiver, and a counted receiver. The protocol is real and populated.

**What is missing.** None of these are constructible from HC source, none are
values a program can hold or pass, and `is.lexical` marks them as lexer
machinery rather than language surface. `LexPipe` carries a `level` and
implements `IPerformer`; that is implementation shape, and exposing it as the
way to spell a receiver freezes it.

**Is a receiver a value or a machine?** The `Sigilizer` is deliberately
stateless because the _frames_ hold the lexical state, which means the receiver
instance **is** the state. So if `lines` is a global and a program folds two
resources into it, they share state. Three answers, all defensible:

- The receiver is a factory and the fold constructs a fresh one.
- The fold clones its receiver.
- Receivers are single-use and reuse is an error, spelled as one.

**Does a stateful receiver need an effect marker?** a05c unified the mutation
marker on the trailing underscore. A receiver that accumulates is mutating, so
either it spells that (`lines_`), or its state is internal in the way
`FrameResource`'s store is internal — present but unreachable, therefore not an
effect the program can observe. The second reads better and needs an argument,
not an assumption.

## Track 2: syntax and globals

**The aggregators need none of this.** An empty aggregate literal already is a
receiver, because `apply` accumulates: `“” “h”` answers `“h”` and `[] 1` answers
`[1]`, both verified against 0.14.1. So `& “”` is the whole-content read and
`& []` is the characters, with no name, no global, and no new syntax.

It is a `&` question only: `|` is map, so mapping a character source already
answers an array of characters. Putting an aggregate in a map half-works and
should probably be refused — `[1, 2, 3] | []` answers the same array three
times, because the pushes land but map wraps each answer.

This also settles the "value or machine" question by example: applying a string
answers a new string, applying an array mutates and answers itself, and both
work as receivers. A literal is fresh per evaluation — `[] 9` twice answers
`[9]` twice — so reuse is handled by evaluation semantics rather than by a
factory protocol.

What follows is about **chunkers**, the only receivers that still need spelling.

| Spelling            | Reads as            | Cost                                                   |
| ------------------- | ------------------- | ------------------------------------------------------ |
| bare name in a tier | `'./f.txt' & lines` | none new; needs a tier per #349                        |
| property            | `'./f.txt'.lines`   | **breaks a10's inertness** — see below                 |
| a new operator      | `'./f.txt' ⊳ lines` | glyph budget, with no evident win over a name          |
| `<-`                | `.x <- './f.hc'`    | already prose-specified; may already be the fold       |
| generalized `&`     | `'./f.txt' & lines` | needs the block-versus-receiver slot question answered |

**The property spelling is a trap worth recording.** a10 is careful that
decomposing a resource is inert: `'https://…'.authority` performs no access.
Spelling a read as `.lines` on the same frame makes `.` sometimes-effectful, and
a reader cannot tell which by looking. Rejected unless someone argues it.

**`<-` may already be the fold operator.** It is prose-specified for module
load, and a11 says a module load is a character fold whose receiver is
parse-and-eval. So `<-` might be the fold with one receiver hard-wired. The open
question is whether it generalizes to take any receiver, or stays the
eval-shaped special case with a general fold beside it.

**The unification worth taking seriously: a block already is a receiver.** `&`
hands a block the element with the accumulator in the parameter slot and takes a
new accumulator back. That is a fold step. If receivers are blocks, there is one
concept rather than two, chunkers are blocks that accumulate, and the lexical
protocol becomes an optimization rather than a competing idea.

Its price is precise and known: **blocks have no end-of-input story.** What
flushes a partial chunk when the characters run out? That is exactly what
`finishInput` provides and what the application protocol lacks. So the
unification costs blocks a completion step — and if blocks get one, that is a
change to the language, not to resources.

## Track 3: integration with the existing eval objects

**What is there.** `HCEval` with `call` / `finish` / `error`, pending-lexeme
state, and line splitting. The pipe chain beneath it. `HCTest`. `cli/runfile.ts`
reassembling partial lines out of host buffers. `cli/prompt.ts` driving the
REPL.

**The prize.** One path for REPL input, piped stdin, a file read, and a module
load. `runfile.ts`'s hand-rolled buffer reassembly stops being anything, because
the receiver protocol is already resumable.

**Two receivers nobody counted, both in production:**

- **The opaque document receiver.** `LexRun` sets `is.document` from
  `RUN_OPAQUE`, so a backtick-fenced document is a receiver that treats its body
  as foreign text and does not look for HC structure inside it.
  Prose-versus-code chunking is already a receiver behavior.
- **`HCTest`.** It chunks a document on `;` and `#` markers, evaluates,
  compares, counts, and emits notes — a chunk-and-eval receiver running in
  production today. It also already knows to stay inert inside fenced documents,
  which is receiver composition working.

**Questions.** `HCEval` is not a `Frame`; does it become one, or does the fold
target the pipes underneath it? These objects take `out` in their constructors,
so a fold that _answers a value_ and a receiver that _emits to an out_ are
different shapes — which one wins? And the security question a11 leaves open
gets a name here: an eval receiver that a program can construct and aim at a
resource is precisely the "what scope does loaded code see" problem.

## Cross-cutting questions

- **Threading.** Accumulator as parameter with the receiver fixed, which is what
  `&` does, or accumulator as receiver, which is what makes an aggregate literal
  work. Verified: `[1, 2, 3] & []` answers `[2, 3]` and `[1, 2, 3] & “”` answers
  `“3”`, so the current threading ignores an aggregate in that slot. Adopting
  the literals means changing it.
- **Reuse.** Answered for literals by evaluation freshness. Still open for a
  named or host-supplied chunker: fresh per fold, cloned, or
  single-use-and-say-so.
- **Completion.** The end-of-input flush. The lexical and pipe protocols have
  one; application does not. This is the sharpest difference between the three.
- **Effect marking.** Whether receiver state is an observable effect.
- **Tiers.** Where receiver names live, given #349's `$` and `$$` and a07 §7's
  rule that an unnameable tier is a defect.
- **Refusal mid-fold.** `Malformed` absorbs every subsequent character by
  returning itself. That is the existing answer to "what does a receiver do
  after it fails," and it may be the model for a refusal arriving mid-stream
  (#338).
- **Answer or emit.** Does a fold return a value, or emit through an `out`? The
  pipes do the latter; `|` and `&` do the former.
- **Resource as receiver.** A resource is a frame, application already writes,
  so folding one resource into another is a copy with no new primitive. Elegant
  or a trap, but it should not happen by accident.

## What would actually settle this

Pick the corpus spelling first. `cli/hc/resources.hc` needs a clean way to say
"give me the whole content," and whatever reads well there constrains all three
tracks harder than any amount of protocol reasoning will. The protocol question
is genuinely open; the ergonomic question has a right answer that a reader can
recognize on sight.
