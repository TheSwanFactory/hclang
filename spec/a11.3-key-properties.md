# Keys Name Properties; They Do Not Create Elements

**Status:** Minimax design proposal, not implemented. This chooses the smallest
representation that gives the dominant forms their obvious meaning and gives the
edge cases one rule rather than complete generality.\
**Issues:** [#368](https://github.com/TheSwanFactory/hclang/issues/368) and
[#374](https://github.com/TheSwanFactory/hclang/issues/374).\
**Builds on:** [`a11.2`](a11.2-declaration-receipt.md), which diagnoses the data
plane serving as both contents and a failed source record. This document
chooses: **the data plane is contents. Evaluated values render canonically;
exact source belongs to parsed syntax.**\
**Reviewed by:** [`a11.4`](a11.4-apply-new-review.md), which read the tutorial
against this proposal and found that "public property" was carrying an
unadmitted exclusion. Its findings are resolved in §6 and in
[Two iteration views](#two-iteration-views).

## The decision

A successful declaration creates or replaces one property. It does **not** also
create a positional element, whether the declaration was terminated by `;` or
`,`.

```hc
[.meta 1; 2, 3]
```

has exactly this value:

- properties: `meta` → `1`
- elements: `[2, 3]`
- lookup: `.meta` answers `1`
- indices: `.0` answers `2`, `.1` answers `3`
- canonical rendering: `[2, 3, .meta 1;]`

The separation does not lose `meta` from iteration. It makes the requested view
explicit: `&` maps the elements `2`, `3`, while `&&` maps the complete
addressable entries `[“meta”, 1]`, `[0, 2]`, `[1, 3]`. `|` and `||` make the
same element-versus-complete-entry choice for folds.

That is the overwhelmingly common case, and it gets the shortest rule.

If one value should be both named and positional, say both operations:

```hc
[.a 1; a, 2]
```

has property `a` → `1` and elements `[1, 2]`. There is no implicit association
between the key `a` and element zero.

This is the minimax trade: the uncommon dual-membership case costs one explicit
read; every value avoids a third structure that has to keep names and indices in
sync forever.

## Why this is minimax

The more general design makes a comma declaration both keyed and positional:
`[.a 1, 9, .a 2]` would have one logical keyed slot holding `2` plus the
positional `9`. Implementing that honestly needs a persistent `key → data-index`
map.

That map cannot be a construction-time convenience. A later write through a
handle has to update the slot; a statement rebind has to update a slot that a
comma established earlier; copy-on-write has to copy it; nested aliasing has to
preserve it; equality, printing, indexing, flattening, and iteration all have to
agree with it. A transient map is worse than no map because it becomes stale as
soon as construction ends.

The benefit is implicit dual membership, which the common case does not want.
The cost is a third permanent plane on every aggregate. Rejected.

The minimax representation uses what exists:

- `FrameList.data` is ordered positional membership.
- `MetaFrame.meta` is named property lookup.
- declaration evidence is transient evaluator state, not membership.

No keyed slot, stored pair, or source-record plane is added.

## Normative rules

### 1. Declaration remains application

`.a 1` is still the setter `a` applied to `1`. The evaluator chooses an explicit
write target, applies schema, visibility, constant, parent, and effect rules,
and writes the property dictionary. There is no assignment special form.

The setter may produce internal evidence containing target, key, and value. `^`
needs that evidence to replace a provisional signature binding. The evidence
survives ordinary expression evaluation long enough to be consumed, but an
aggregate constructor does not admit successful declaration evidence as an
element.

### 2. One key denotes one property

A successful rebind replaces the value of the resolved physical key. It never
adds a second logical property and never adds an element.

```hc
[.a 1, .a 2]
(.a 1, .a 2)
```

both have the effective property set `a` → `2` and no positional elements. Their
container shells remain different; their property set is the same.

For ordinary named keys, the first declaration fixes canonical property order
and a rebind changes the value in place. Constants, schema failures, visibility
failures, and parent refusals still refuse rather than overwrite.

### 3. Positional membership is explicit

Only a value expression that is not consumed as a successful declaration result
becomes an element. Unkeyed values retain source order and duplicates.

```hc
[.a 1; a, a, 2]
```

has elements `[1, 1, 2]`. Properties do not silently deduplicate unkeyed values,
and unkeyed values do not acquire property names by position.

This document does not make `()` a set. `[]` remains an ordered list, `()`
remains grouping/nil as implemented, and
[#374](https://github.com/TheSwanFactory/hclang/issues/374) owns any ordered-set
design.

### 4. Separators keep their evaluation meaning

`;` still marks a statement and `,` still marks an expression. This proposal
does not erase that distinction and does not decide whether every plain
statement should be non-enumerable.

It makes one narrower ruling: a successful declaration result is property-write
evidence, not element data, under either separator. Thus `.a 1,` does not mean
"write `a` and implicitly append `1`." Write the later `a` explicitly when that
is wanted.

Ordinary statement results such as `[1; 2;]` remain unchanged by this proposal.
Suppressing every statement may be coherent with `doc/GRAMMAR.md`, but it is a
larger language change and is not required to fix keys.

### 5. Failures are values and are never hidden

Only a **successful** declaration result is omitted. A failed constant rebind,
schema mismatch, missing parent, or refused effect remains observable at the
position where evaluation failed. A constructor must not turn

```hc
[.A 1; .A 2;]
```

into an apparently successful object containing only `A` → `1`.

The property may retain its last valid value; the aggregate result still carries
the failure under the ordinary failure-propagation rules.

### 6. An entry is a declared property, not every metadata slot

`meta` is the implementation store. Three kinds of thing live in it, and only
one of them is an entry:

1. **Declared properties.** A write a declaration in the program performed.
   These are the entries.
2. **Interpreter bookkeeping.** Structural parent links, the setter output
   target `>>`, schema companions such as `a.<>`. Not independent properties,
   never entries.
3. **Type-published derived components.** Values a type computes from the
   value's own data at construction and caches in the store because the store is
   where readable names live. Readable, never entries.

The third category is the one a11.4 caught this proposal owing an answer for.
Per [`a10`](a10-resource-primitive.md) a resource publishes its RFC 3986
components — `scheme`, `authority`, `path`, `query`, `fragment` — as ordinary
readable properties, and `FrameURI` implements that by writing them into `meta`
while decomposing the reference. Under a rule that enumerated every visible
property, `'./out.txt' && {_}` would emit `[“path”, “./out.txt”]` before any
character.

That is wrong, and the reason is not visibility. `.path` is derived from the
reference the value **is**; a declared property is a binding a program wrote
into the contents the value **holds**. Enumeration is over contents. So the line
is **declared versus derived**, not public versus private, and it is drawn where
the implementation already draws it: a declaration's write is an entry, a
constructor's decomposition is not.

Visibility then applies on top, unchanged: enumeration follows the same
public/protected/private decision as lookup, so a caller enumerates exactly the
declared properties it could have read by name. A raw `Object.entries(meta)`
remains an implementation primitive rather than the language contract.

Integer keys on a list are indices, so a numeric property declaration on a list
refuses rather than creating a property that `.0` cannot read. The refusal is
unconditional rather than conditional on a collision existing at the time, for
the reason given under [Two iteration views](#two-iteration-views).

### 7. Rendering is canonical value rendering

The evaluated value does not reconstruct its source. Positional elements render
in order, followed by its declared properties in canonical property order. That
is why the dominant example renders as:

```hc
[2, 3, .meta 1;]
```

rather than reproducing `[.meta 1; 2, 3]`.

This gives `toString()` one honest answer. Exact separator placement and source
order belong to the parsed frame graph or a parse-only receiver. a07's manifest
claim requires external identities to be extractable before evaluation; it does
not require an evaluated value to reconstruct source text.

### 8. Equality keeps the planes explicit

- `==` compares actual positional data, with no declaration-echo filtering.
- `===` compares declared properties.
- `=` compares the canonical combined value.

Source equality, if ever required, is an operation on parsed syntax rather than
on an evaluated value.

## The common cases

| Source            | Elements     | Properties    | Canonical value    |
| ----------------- | ------------ | ------------- | ------------------ |
| `[.meta 1; 2, 3]` | `[2, 3]`     | `meta → 1`    | `[2, 3, .meta 1;]` |
| `[.a 1; a, 2]`    | `[1, 2]`     | `a → 1`       | `[1, 2, .a 1;]`    |
| `[.a 1, .a 2]`    | `[]`         | `a → 2`       | `[.a 2;]`          |
| `[.a 1; .a 2;]`   | `[]`         | `a → 2`       | `[.a 2;]`          |
| `[.a 1, 9, .a 2]` | `[9]`        | `a → 2`       | `[9, .a 2;]`       |
| `[1, 1, 2]`       | `[1, 1, 2]`  | none          | `[1, 1, 2]`        |
| `[[.a 1;], 2]`    | `[inner, 2]` | inner `a → 1` | `[[.a 1;], 2]`     |

The last row is attenuation by construction in a different sense: the innermost
aggregate is the declaration target. Its property never leaks onto the outer
list.

## Parentheses and the single object

The useful existing distinction stays:

```hc
(x)  → x
[x]  → [x]
```

Property ownership limits unboxing. A group with properties is an object and
cannot disappear merely because declaration evidence was removed from its data.
Therefore:

- `()` remains nil.
- `(x)` unboxes only when the group acquired no properties.
- `(.a 1)` is a property-bearing, zero-element group with `a` → `1`; it is not
  nil and does not attach `a` to an interned declaration receipt.
- `(.meta 1; x)` remains a property-bearing group in this minimax version rather
  than copying `meta` onto `x`.
- `[x]` and `[.meta 1; x]` always remain boxed lists.

The last two rules are deliberately conservative. Unboxing a property-bearing
single value requires an identity-safe "decorate this scalar" operation; atoms
are otherwise shareable, and some are interned. Keeping the owning group is less
magical and can be relaxed later without changing property membership.

Multi-value `()` as an ordered set is #374 and does not change these ownership
rules.

## Two iteration views

The representation keeps properties and positional data separate; the operator
surface chooses between two coherent views of that value:

|                     | map results | fold into one result      |
| ------------------- | ----------- | ------------------------- |
| positional elements | `&`         | <code>&#124;</code>       |
| complete entries    | `&&`        | <code>&#124;&#124;</code> |

Two nouns, used consistently here and in the tutorial. A **positional element**
is a member of the ordered data plane. A **complete entry** is one item of the
whole addressable surface:

1. declared properties, in canonical property order, as `(name, value)`;
2. positional elements, in index order, as `(index, value)`.

Each doubled form exposes its entry as a synthesized `[key-or-index, value]`
tuple. The tuple is never stored in the source value. A declaration creates one
property entry in this complete view, but it does not create a positional entry
unless the program explicitly reads the property as an element.

Therefore:

```hc
[.meta 1; 2, 3] & {_}   → [2, 3]
[.meta 1; 2, 3] && {_}  → [[“meta”, 1], [0, 2], [1, 3]]
[.meta 1; 2, 3] | []    → [2, 3]
[.meta 1; 2, 3] || []   → [[“meta”, 1], [0, 2], [1, 3]]
```

This preserves both user-visible address spaces without making a pair the
representation of a property. It also makes identity complete-entry iteration an
actual identity over entries rather than the current lossy `(.a 1, .b 2) && {_}`
→ `[1, 2]` accident.

These are the proposal's glyph assignments, shared with a11.1 and the
aspirational `cli/hc/apply-new.hc`. They deliberately differ from v0.14.1; the
current behavior remains documented in `cli/hc/apply.hc`.

### What each slot carries

`&&` is what forces the tuple. A map hands its block one argument, so a
complete-entry map has exactly one slot in which to deliver both the address and
the value; packaging them is the only option that does not silently drop one.
That representation then fixes the rest of the surface.

- **A single map exposes only the element.** The parameter slot carries no
  index. v0.14.1's indexed map, `[1, 2, 3] | {. }` → `[0, 1, 2]`, becomes
  `[1, 2, 3] && {_.0}`. This is an ergonomic cost accepted deliberately: if `&`
  also supplied an index, `&&` would be redundant for property-free lists and
  the two axes would collapse into one.
- **A single fold seeds from the first element**, so a one-element fold is that
  element and an empty block fold is nil.
- **A complete-entry fold requires a value seed**, and applies each entry to the
  value accumulated so far. First-entry seeding would make the initial
  accumulator a `[key, value]` tuple while every later accumulator is whatever
  the step answered, so a block form has no coherent shape and refuses. No legal
  `||` binds a parameter slot at all.
- **An aggregate seed belongs to a fold, not a map.** A map wraps one answer per
  input, so an aggregate there would hand every input an alias of one
  accumulator and answer repeated aliases. It refuses instead.
- **A value seed is threaded as the receiver**, which is a11's second threading
  option; a block fold keeps a11's first, the accumulator in the parameter slot.
  The proposal takes both and discriminates by operand kind. For a value seed
  `apply.hc`'s distinction then governs: an aggregate seed answers itself and is
  mutated, while a text seed answers a new value. A literal seed is fresh per
  evaluation; a named seed is not insulated.

### What the numeric-key refusal is for

Because a complete entry puts a name and an index in the same slot, an entry's
address has to name exactly one thing. A block can always tell the two apart by
type — a property key is text, an index is an integer — so dispatch is not the
problem. Ambiguous addressing is: a numeric property that `.0` cannot read gives
one address two meanings, and an entry stream is where that becomes visible.

The refusal is therefore unconditional on a list, not conditional on a present
collision. A construction-time collision test would not hold for the value's
lifetime anyway, since appending elements can turn a numeric name that collided
with nothing into one that collides.

### The complete view has no inverse

`&&` answers real nested arrays, so the tuples exist as values even though the
source stores no pairs. Folding them back does not rebuild the value: a11.2
establishes that applying a pair to a frame does not merge, and `(.z 9) (.a 1)`
loses `.z`. There is no round trip through entries, and reconstruction remains a
job for parsed syntax.

### Collections iterate contents; streams iterate content

An aggregate holds its contents, so its complete view is its two address spaces.
A resource does not hold characters — it names content that a read produces —
and per §6 its URI components are derived from the reference rather than
declared into contents. So a doubled read over a resource is indexed characters
only:

```hc
'./out.txt' && {_}  → [[0, “h”], [1, “e”], [2, “l”], [3, “l”], [4, “o”]]
```

Identity metadata never enters a content stream, which keeps a10's inert
decomposition and the effectful read cleanly separated. Whether a chunking
receiver should contribute named entries for the chunks it emits is a receiver
question, and stays with [`a11`](a11-resource-iteration.md) and
[`a11.1`](a11.1-receivers.md).

### How much declared state a resource can actually hold

The declared-versus-derived rule and the character-fold rule would disagree
about a resource carrying a declared property, so that state was checked against
v0.14.1 rather than assumed away. Three results, all observed:

- **A new declared key is unreachable.** `.key v` never targets a resource:
  `FrameName.in` takes its target from the scope's write target, and only
  aggregates under construction, unwrapped handles, a closure's local frame, and
  the file scope are ever that. Inside a closure called with a resource,
  `{.brandnew 1}` answers `.brandnew 1` and writes the closure's own frame.
  Handles wrap only `FrameArray`, so a resource is never a bound-method receiver
  either, and `@newkey 1` answers `$!.name-missing “newkey”` because an alias
  needs an existing owner for the key.
- **An existing derived component can be overwritten.** `@path` is the one
  spellable write that lands, because `FrameAlias` resolves the owner of a key
  that already exists and a URI part is ordinary public metadata.
  `{@path “X”; _.path}` applied to `'./out.txt'` answers `“X”`, and v0.14.1's
  `&&` over that value answers `[“X”]`.
- **It never persists.** `FrameSymbol.in` hands out `value.copy()` for a
  non-aggregate, so the write lands on a per-read copy: after a closure spelled
  `{@path “X”}` runs against a bound `r`, `r.path` is still `“./out.txt”`.

So the two rules cannot disagree about any stored value, because the set of
declared properties on a reachable resource is empty. They could differ only for
a transient copy inside one call, and there the stream rule settles it: the
complete view of a resource is its characters either way.

Two consequences worth keeping. First, **the store cannot tell declared from
derived by itself** — `decompose` and a declaration both go through
`MetaFrame.set` — so "derived" has to be recorded by the type that publishes the
component rather than inferred at enumeration time. Second, that overwrite
leaves a value whose `.path` disagrees with its own printed reference, since
`FrameURI.toString` prints the reference unchanged. Refusing a write to a
derived component is the coherent answer and is recommended, but it is an a10
question about URI values rather than an iteration question, so it is not
decided here.

The authority boundary is unaffected, and that was verified too: after a closure
spelled `{@path “../escape”; _ “oops”}`, the content lands in `out.txt` while
`'./escape'` stays `$!.resource-absent`. Writes follow the private normalized
location, so mutating component metadata cannot redirect I/O.

## Edge cases

| Case                           | Ruling                                          | Why it is tolerable                                    |
| ------------------------------ | ----------------------------------------------- | ------------------------------------------------------ |
| Declaration under `,`          | property only                                   | dual membership is explicit, not punctuation-dependent |
| Rebind after positional read   | property changes; old explicit element does not | there is no hidden alias between planes                |
| Same value named twice         | two properties may point to one value           | keys name bindings, not identities                     |
| Same key rebound               | one property, last valid write wins             | ordinary dictionary behavior                           |
| Numeric property on list       | refuse                                          | index/property shadowing is otherwise unnameable       |
| Schema companion               | not a property entry                            | it describes one property                              |
| Private/protected key          | enumerate only when visible                     | enumeration cannot bypass lookup policy                |
| Successful `.^`                | structural parent only, no element              | parenthood is not membership                           |
| Failed declaration             | preserve failure                                | refusal cannot masquerade as omission                  |
| Bare required signature field  | preserve as structure                           | it is not a completed property write                   |
| Declaration inside nested list | belongs to inner list                           | explicit construction target already supplies the rule |
| Exact source round-trip        | not promised after evaluation                   | parsed syntax owns source fidelity                     |
| Type-published URI component   | readable, not an entry                          | derived from the reference, not declared into contents |
| Doubled read of a resource     | indexed characters only                         | a stream has content, not held contents                |
| Aggregate seed in a map        | refuse                                          | one accumulator cannot serve one-answer-per-input      |
| Block form of a doubled fold   | refuse                                          | a first-entry tuple cannot seed a block accumulator    |
| Named aggregate seed           | mutated, and answers itself                     | application semantics are unchanged by folding         |

The rebind-after-read case is the price of refusing hidden aliases:

```hc
[.a 1; a, .a 2]
```

has element `[1]` and property `a` → `2`. The element is the value explicitly
read at that point; it is not a live view of the property. That is ordinary
value semantics and much easier to explain than a write silently changing
element zero.

## Smallest implementation

No code is prescribed here, but the representation cost is bounded.

1. **Make successful declaration evidence uniform.** First binding, rebinding,
   schema definition, and structural-parent declaration need an internal result
   the collector can recognize. It must retain target/key/value evidence for
   `^`. Errors are never tagged successful.
2. **Project at construction boundaries.** `FrameArray.in` and multi-item
   `FrameGroup.in` evaluate each source expression, perform the property write,
   and omit a direct successful declaration result or a statement wrapper around
   one. They retain every failure and every non-declaration result.
3. **Keep direct evaluation separate.** A declaration evaluated outside an
   aggregate may still answer evidence for tooling or the assigned value later;
   this proposal changes membership, not application chaining.
4. **Keep property-owning groups boxed.** `FrameGroup` unboxes only a
   property-free singleton.
5. **Delete the echo heuristic.** `FrameList.dataString()` no longer compares
   rendered strings against metadata declarations. Its data is already data.
6. **Add a declared-property view.** Lookup, complete-entry iteration,
   rendering, and metadata equality use declared properties filtered by
   visibility; copying may continue to use raw metadata. Since `decompose` and a
   declaration reach the store by the same `MetaFrame.set`, the publishing type
   has to record which keys are derived — `FrameURI.PART_KEYS` already names
   them — rather than leaving enumeration to infer it.
7. **Let a character fold supply its own positions.** Doubling a read indexes
   the characters it produces. Nothing stream-specific is needed to keep a URI
   component out of that stream — §6's declared-versus-derived rule already
   excludes it — so this step is only about where the indices come from.
8. **Leave the object model alone.** Write-target selection, handles,
   copy-on-write, declared parents, schemas, and `MetaFrame.set` remain the
   same.

This is a collector correction plus a property projection. It does not add a
container index, first-class pair, syntax-record plane, or new operator.

## Rejected alternatives

**One value with two indexes.** Best semantics for implicit dual membership, but
requires a permanent key-to-slot map and synchronized mutation after
construction. Too much mechanism for an uncommon shorthand.

**Append every assigned value.** Replaces the receipt log with a value log;
`[.a 1, .a 2]` still has two elements for one effective property.

**Make only `;` property-only.** Preserves comma generality at the cost of the
same keyed-slot problem and makes one declaration's membership depend on its
terminator. The edge case dictates the representation.

**Return assigned values globally and delete receipts.** Breaks `^` and changes
application chaining before membership is fixed. Projection at the aggregate
boundary is smaller.

**Store first-class pairs.** No pair type or pair-merge application exists, and
stored pairs duplicate the key. Iteration can synthesize tuples when requested.

**Store source marks in metadata.** Pollutes lookup, complete-entry iteration,
schema signatures, metadata equality, and flattening with non-properties.

**Add a third syntax plane.** Architecturally clean if exact reconstruction is a
requirement, but evaluated values already fail to reconstruct source and a
parse-only graph serves a07's manifest requirement. Do not pay for fidelity that
is not part of value semantics.

**Make `()` a set here.** Valuable enough for #374, but it requires separating
parser grouping from runtime collection and choosing dedup equality. It is not
needed to fix properties.

**Suppress every statement.** Consistent with the grammar's "non-enumerable"
wording, but changes closures, statement results, doctests, and failure flow.
Declaration evidence can be removed without taking that larger decision.

**Enumerate every visible metadata entry.** The rule a11.4 tested this proposal
against, and it fails on the first resource: `'./out.txt' && {_}` would answer
identity components before any character. Rejecting it costs one distinction —
declared versus derived — and buys a content-only complete view.

**Give a resource a hybrid doubled view.** Properties of the reference followed
by characters of the content is spellable, but it mixes an inert decomposition
with an effectful read in one stream and makes the doubled form mean something
different for streams than for collections. Named reads already serve the
identity half.

## Acceptance boundary

This proposal succeeds if all of these can be true at once:

1. `[.meta 1; 2, 3]` iterates exactly `2`, `3` through `&`/`|` and still answers
   `.meta` as `1`.
2. The same value iterates `[“meta”, 1]`, `[0, 2]`, `[1, 3]` through `&&`/`||`.
3. Rebinding a key never creates or mutates a positional element implicitly.
4. A value can be named and positional with one explicit read.
5. `^`, schema enforcement, constants, visibility, handles, and failures keep
   their existing authority and refusal behavior.
6. `==` needs no declaration-string heuristic, and `==`/`===`/`=` keep answering
   for data, properties, and the canonical value respectively.
7. Complete-entry iteration receives key/index plus value without storing
   duplicate pairs.
8. No third persistent plane is introduced.
9. A resource's complete view is its characters; its RFC 3986 components stay
   readable and inert, and never appear as entries.
10. An index remains reachable — through `&&`, not through a single map's
    parameter slot.
11. Every refusal the surface depends on is a refusal: numeric key, aggregate
    seed in a map, and block form of a doubled fold.

If a later use case proves that implicit keyed-and-positional membership is
worth a permanent slot map, it can be added as an explicit ordered-dictionary
type. The base `Frame` does not need to pay that cost first.
