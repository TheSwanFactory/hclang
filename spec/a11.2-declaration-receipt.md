# The Data Plane Owes Two Answers

**Status:** Diagnosis. Nothing decided. This names a defect older than
[#368](https://github.com/TheSwanFactory/hclang/issues/368) and upstream of it,
so it wants its own ticket rather than living inside that one.\
**Relation:** [`a11`](a11-resource-iteration.md) asks what `|` and `&` iterate,
and [`a11.1`](a11.1-receivers.md) asks what a receiver is. Neither can be
settled while the thing being iterated is partly a value and partly a record of
how it was written. [#374](https://github.com/TheSwanFactory/hclang/issues/374)
runs into the same tangle from the container side.\
**Thesis:** The data plane is asked for two answers — what the value contains,
and how the source spelled it — and it gives neither correctly. The declaration
receipt is the symptom most often noticed; it is not the disease.

Every behavior cited below is verified against 0.14.1, and the current-behavior
half is an executable corpus in `cli/hc/apply.hc`.

## The insight, and what it cost

Two claims sit at the base of HC. `;` marks a statement and `,` marks an
expression. And `.a 2` is not assignment syntax — it is an evaluation, the
setter `a` applied to `2`. Together they are the homoiconic position:
declaration is application, so a program is a frame graph with no special forms
in it.

But name lookup needs a real dictionary. Reading `.a` has to be direct rather
than a scan, rebinding has to replace rather than append, and a schema has to be
findable beside its value. So metadata became a dictionary — while the
declaration, being an evaluation, still had to produce a value.

Both survived. That is the confusion.

## The mechanism

`FrameSymbol.apply` performs the write and then answers a record of it:

```
out.set(assignmentKey, argument);              // the dictionary write
return previous.is.missing
  ? new FrameLiteral(`.${this.data} …`, { target: new WeakRef(out), key, value })
  : argument;                                  // a receipt of the write
```

`FrameArray.apply` collects any non-void argument, so the receipt lands in the
data plane. An aggregate therefore holds the dictionary **and a log of the
writes that built it**.

The delimiter has to be isolated from the bracket to see this, because the two
are independent and only one of them matters. Paren and square behave
identically; `,` and `;` do not.

| Source          | Answers                         | Data plane, via `\| {_}` |
| --------------- | ------------------------------- | ------------------------ |
| `.a 1`          | `.a 1`                          | —                        |
| `(.a 1, .b 2)`  | `(.a 1, .b 2, .a 1; .b 2;)`     | `[.a 1, .b 2]`           |
| `(.a 1; .b 2;)` | `((.a 1); (.b 2); .a 1; .b 2;)` | `[(.a 1); (.b 2);]`      |
| `[.a 1, .b 2]`  | `[.a 1, .b 2, .a 1; .b 2;]`     | `[.a 1, .b 2]`           |
| `[.a 1; .b 2;]` | `[(.a 1); (.b 2); .a 1; .b 2;]` | `[(.a 1); (.b 2);]`      |
| `[1, 2]`        | `[1, 2]`                        | `[1, 2]`                 |
| `[1; 2;]`       | `[(1); (2);]`                   | `[(1); (2);]`            |

So the two delimiters do distinct, consistent things, and neither of them is
suppression:

- **`,` retains the element bare.** A declaration under a comma contributes its
  receipt, `.a 1`, as an ordinary element.
- **`;` retains the element wrapped in a group and marked.** A declaration under
  a semicolon contributes `(.a 1);`.

The wrapping is not declaration-specific: `[1; 2;]` answers `[(1); (2);]`, so a
statement wraps whatever value it terminates. `FrameExpr.asStatement` does the
wrapping and `FrameList.toStringDataArray` reads `obj.is.statement` back to
choose `;` or `,` when printing. That is coherent, and it tells us what the
retained element is _for_.

## What the retained element is for, and why it fails anyway

The mark exists so a value can print back as the source that produced it. A
program is data, so round-tripping is not a nicety. That is the second answer
the data plane owes: not just the contents, but the spelling.

It does not deliver it. Key override is the shortest proof, because the two
answers diverge in one line:

| Reading          | `[.a 1, .a 2]` gives | Verdict                  |
| ---------------- | -------------------- | ------------------------ |
| the name index   | `a` → `2`            | correct                  |
| the data plane   | `[.a 1, 2]`          | two entries for one name |
| the printed form | `[.a 1, 2, .a 2;]`   | not what was written     |

As contents it is a write log, and an inconsistently typed one: a receipt for
the first declaration and a bare `2` for the second, because rebinding answers
the argument rather than a receipt. As a syntax record it is wrong too — the
source was `[.a 1, .a 2]`.

Nor does round-tripping hold in the simple case. `[.meta 1; 2, 3]` answers
`[(.meta 1); 2, 3, .meta 1;]`: the delimiters survive, but the group wrapper and
the metadata suffix do not appear in the source. So the syntax answer is partial
at best and false under rebinding.

**Both answers are owed to one plane, and neither arrives.** That is the defect.
Choosing which answer the data plane should give — and where the other one lives
— is the decision this document exists to frame.

## What the code adds to the diagnosis

**The statement/expression distinction is intact; the plane it writes into is
not.** `;` wraps and marks, `,` leaves bare, and both retain — a real
distinction, applied uniformly to declarations and plain values alike. Nothing
here argues for changing what `;` _means_. The question is only whether its
record belongs in the data plane.

**Display suppression already exists, and only at the top level.** `hc-log.ts`
skips anything `is.statement`, which is why `.a 1;` prints nothing at the REPL
while `[.a 1;]` retains `(.a 1);`. The intent that a statement's value is not
the point is already implemented — just not inside aggregates.

**One form answers two kinds of thing.** The receipt comes back only when
`previous.is.missing`; a rebinding answers the argument. So `.a 1` answers
`.a 1` on first declaration and `.a 2` answers `2` on the second — one syntax,
two result types, discriminated by invisible prior state.

**The receipt has exactly one consumer.** `FrameLiteral.binding` is read by
`BindType` — the `^` operator in `lib/ops/type-operations.ts` — and nowhere else
in `lib/`. It derefs the target, calls `bindSignature` on the closure, and
re-sets the key, which is how `.f (sig) ^ {body}` replaces a provisional binding
with a validated one. The vestigial log in every aggregate exists to give that
one operator an lvalue.

Two further facts, because they close off the obvious escapes:

- **The receipt is not a pair.** `(.a 1).a` answers `1`, but that is the _group_
  answering; `[.a 1, .b 2] | {_.a}` answers `$!.name-missing`, and neither
  `.key` nor `.value` exists. A receipt records a write; it is not a first-class
  pair.
- **Applying a pair does not merge.** `(.z 9) (.a 1)` answers `(.a 1, .a 1;)`
  and `.z` is gone, because `Frame.apply` defaults to answering its argument. So
  folding pairs back into a frame does not rebuild a dictionary.

## Why this is upstream of #368

#368 asks what `|` and `&` iterate. Every answer has been unstable, and this is
why: the thing being iterated has two planes whose division of labor is not
stated anywhere. `(.a 1, .b 2) && {_}` answering `[1, 2]` does not read as
nonsense because `&&` is misnamed. It reads as nonsense because its source holds
a dictionary and a write log, and the operator has to pick one without being
told which is the value.

A keyed-versus-unkeyed operator split — a11.1's most promising idea — cannot be
designed against such a value. Fix the value first.

#374 arrives at the same place from the container side: it wants `()` to be a
set so that container type says what a key is, and finds `FrameExpr` serving as
both the paren value and the statement-wrapping machinery. That is this defect
wearing different clothes. One class is answering for the value and for the
syntax, and every attempt to give iteration a clean source runs into it.

## The question, stated correctly

The tempting question is "what should `.a 1` evaluate to," and it is the wrong
lever. It treats the receipt as the defect, so every answer pays to rebuild `^`
while leaving the plane still owing two answers.

The right question is **where the syntax record lives, if not in the data
plane.** Answer that and the receipt question mostly dissolves, because the only
reason a declaration's value had to be a record was that the plane collecting it
was doubling as the record.

| Where the spelling lives             | The data plane becomes | Principal cost                   |
| ------------------------------------ | ---------------------- | -------------------------------- |
| nowhere — round-tripping is given up | the contents, cleanly  | a program stops being fully data |
| beside the value, in metadata        | the contents, cleanly  | metadata now holds two kinds     |
| in the aggregate, as one record      | the contents, cleanly  | a new field on aggregates        |
| stays in the data plane (today)      | contents _and_ record  | neither answer is correct        |

**Giving up round-tripping** is the cheapest change and the most expensive
principle. a07 §5 rests on a program being readable as data — "the program is
the manifest" — so a value that cannot print back as its source weakens a
security claim, not just an ergonomic one.

**Beside the value in metadata** is the smallest honest move. The delimiter that
terminated an element is a fact about that element, and metadata already holds
facts about elements. Cost: metadata stops being purely the name index, which is
the thing #374 wants it to be.

**One record on the aggregate** keeps both planes pure and puts the spelling
where it actually belongs — the aggregate is what was written, and the
delimiters are a property of the writing, not of any element. Cost: a third
place to store things, and it must survive `instanceCopy` and `in()`.

The third is the one to beat. It is also the only one that makes the two answers
independent, so a change to either stops breaking the other.

## What a declaration then answers

Once the plane is not a record, this is a smaller and separable choice.

The value assigned — `.a 1` answers `1` — becomes available without paying for
it: the data plane holds the values in insertion order, the metadata holds the
same values by name, and the two planes are **one value with two indexes**
rather than two stores. That is an ordered dictionary, which is the structure
the implementation reached for when it needed proper dictionaries for metadata.

Under it, `[.a 1, .a 2]` holds data `[2]` and `a` → `2`: one entry, matching
what the value effectively already is. The rebinding inconsistency disappears,
because the answer stops depending on whether the name was bound.

The alternatives stay on the table and stay cheaper than they were, since none
of them now has to carry the syntax:

- **Void.** Cleanest, and retreats from "declaration is application" by making
  one application yield nothing.
- **A pair.** Makes a11.1's tuple proposal native, but a pair type has to exist,
  the key is stored twice, and pair application would have to merge — which it
  does not.

It keeps the insight either way: `.a 1` stays an evaluation and stays
application, so nothing becomes a special form. And it makes a11's operator
questions answer themselves — `& {_}` answers `[1, 2]`, values positionally,
which is what `&&` answers today but arrived at honestly, while `&& {_}`
synthesizes pairs from the two indexes rather than storing them.

## What it costs

Separating the syntax record is the smaller half. The larger cost sits with `^`,
and only if the receipt goes away: it needs the declaration's target and key,
which are properties of the **evaluation site**, not of the value, and today it
receives them smuggled through the data plane. That is a real refactor.

Note the sequencing this implies. Moving the syntax record out of the data plane
does **not** require touching `^`, because the receipt can stay exactly as it is
while the plane stops doubling as a record. So the two changes are independent
and the cheap one comes first.

Every corpus expectation spelled `; .a 1` / `# .a 1` changes only under the
receipt half, `testdoc.hc` included.

## The case that decides it

The aggregate that mixes a declared and an undeclared element. This is not the
statement/expression mix, which works: `[.a 1, 2]` answers a data plane of
`[.a 1, 2]`, a receipt beside a plain value, both under commas.

Under a value-answering declaration that data plane becomes `[1, 2]`, with `a`
bound to `1` in the name index and nothing marking which element carried the
name. Two readings, and they point opposite ways:

- **Correct.** A value is a value. Whether it also acquired a name is the
  metadata's business, and asking the data plane to remember is the original
  error repeating itself.
- **Fatal.** Insertion order interleaves named and unnamed values, so neither
  plane reconstructs the source.

Note what the reframing does to this. The "fatal" reading is only fatal while
round-tripping is the data plane's job. Move the syntax record out and the
objection moves with it — reconstruction becomes the record's problem, and the
data plane is free to be nothing but contents. So the deciding case for the
receipt half is decided _by_ the syntax half, which is another reason to do that
one first.

## Not resolved here

- Where exactly the syntax record goes, if it becomes one record on the
  aggregate. It has to survive `instanceCopy` and `in()`, and it must not become
  a third lookup tier, which a07 §7 would call a defect.
- Whether a statement's value should be suppressed rather than wrapped. Not a
  defect — the wrapping is consistent — but it is a live question, and fully
  separable from what a declaration answers.
- Whether an aggregate should refuse to mix declared and undeclared elements.
- Whether `^` should keep its current form at all, given that it exists to amend
  a binding after the fact.
- How much round-tripping is actually owed. a07 §5 needs a program's _external
  identities_ to be extractable, which is weaker than byte-exact source
  recovery. If the weaker claim suffices, the first option in the table stops
  being a principle sacrifice and becomes the cheapest correct answer.
